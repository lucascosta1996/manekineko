# V9/V10 execution and Sepolia rehearsal adapters

The separate `season:run:mainnet` and `season:run:sepolia` commands pin their networks and share lifecycle modules. Only the Sepolia entry point can supply the rehearsal adapter; Mainnet does not load it and rejects test flags and saved rehearsal state before service access. Mainnet waits for real buyers. The legacy `season:run -- --chain …` command dispatches to the same entry points. Chain and rehearsal adapters do not submit transactions merely because they are imported. `execute` plus an explicit local signing key, chain profile, fee ceiling, total spending cap and durable journal are required for every transaction. Supported execution chains are Ethereum Mainnet `1` and Sepolia `11155111`; rehearsal wallets are strictly Sepolia-only.

## Chain adapter

`createVersionedChainAdapter` in `chain.ts` selects an exact policy from the immutable prepared artifact. `createV10ChainAdapter` loads V10 factory, renderer, split deployer and round artifacts plus Eligibility V5 / Winner Credits V6. `createV9ChainAdapter` preserves V9 with Eligibility V4 / Winner Credits V5. Shared `version.ts` defines the exact pairs; there is no fallback between their pins. Build metadata must identify Solidity 0.8.37 and Cancun. The adapter checks exact executable runtime, canonical registry code hashes, factory renderer/deployer relationships, both immutable round creation-code pieces, operator ownership, the coordinator's live key/limits and every deployed round constructor getter. V10 is `affiliate-v10` / `unique-rank-v6`; V9 remains `affiliate-v9` / `unique-rank-v5`. Both enforce fixed cumulative 20 primary mints per recipient. V10 combinations identify tokens from mint and final scores remain separate reads.

Public operations:

- `preflight(payload?)`: read-only owner, registry and optional future-constructor checks.
- `ensureFactory(key, existingFactory?)`: import reviewed history if configured, deploy or verify the selected version’s factory, approve it in both canonical registries.
- `deployCollection(key, payload, factory)`: freeze the resolved constructor once, deploy exactly that round, verify it, register eligibility and winner credits, fund VRF and optional sponsorship, return public deployment data.
- `snapshot(round)`: one confirmed canonical block, lifecycle/counters, independent prize claim states and current winner holders. A sold-out event is never proof of a paid prize.
- `advance(key, round)`: at most one activation, randomness request, bounded eight-attempt finalization or expired-round cancellation per call. Activation uses the latest block's time after confirmed owner/version/readiness checks; social facts remain confirmed.

The factory requires the preceding round to have sold out, revealed and retained all protected liabilities. An unsold round cannot roll into another collection in that factory. The runner must handle the refund outcome explicitly. Immutable `saleStartAt` cannot move earlier when affiliate positions fill. Holders claim their own prizes and refunds; the production adapter never mints or claims for them.

## Registry migration

`setupVersionedRegistries` in `chain-setup.ts` has a separate persisted setup journal. V10 setup deploys Eligibility V5 / Winner Credits V6; explicit V9 setup preserves V4/V5. The CLI setup JSON requires `contractVersion: "affiliate-v10"` for V10, while omission intentionally preserves existing V9 recovery. Never reuse a V9 journal or relabel its registry addresses as V10.

An existing network requires the reviewed prior credits registry and completed historical source factory/round pins. V10 accepts exact completed V6–V9 source pairs; V9 accepts its completed V8 source. Every ledger in the previous-registry lineage must pass reviewed runtime/version/root checks and have no sponsorship balance or registered destination that can still mint. V10 setup and unsigned operations invoke the same canonical retirement verifier before producing or sending migration actions. Zero balance alone is not retirement: anyone can fund it again. Stop old sponsorship automation and keep prior registry governance retired so it cannot register new mintable destinations. Setup never withdraws prior funds. A fresh network must explicitly select `freshNetwork` and provide no historical imports.

Historical rounds import as source-only where required, preserving their original registry/version and prior holder rights. Imports complete before any new target can consume bootstrap. Source rewards are registered in the selected new Winner Credits registry, whose previous-registry link preserves lifetime redemption history. Unfinished/refunded sources are rejected.

V10 runtime preflight and every adapter write recheck the complete predecessor lineage at a confirmed block: compiled runtime, descending V5–V2 versions, preserved historical root, zero sponsorship and permanently closed destinations. Only the same canonical block hash can reuse a successful check. Persisted transaction replay rechecks preflight after receipt reconciliation as well. This catches old targets registered after setup; governance must still prevent concurrent new registrations on retired ledgers. The verifier needs historical code and complete bounded registration-log reads, so unavailable archive data fails closed. V9 recovery retains its original checks.

`ChainPendingError` means the exact transaction is signed and/or submitted but not yet sufficiently confirmed. Resume the same setup/run; never create a replacement journal to make the error disappear. Source support and a passing local migration test do not prove that any registry is deployed or migrated on a live chain.

## Durable transaction and concurrency contract

The caller must hold one exclusive lock for the entire run **and the operator signer**. `chain-transactions.ts` saves signed bytes, nonce and deterministic hash before broadcast, reconciles the exact hash after a crash, verifies canonical successful receipts, checks the same chain/signer, rejects outside nonce changes, preserves EIP-1559 fee ceilings and accounts for transaction value plus gas. It never increases fees or replaces a pending transaction automatically. A durable save error poisons that pipeline instance; reload the stored run before retrying.

`saveJournal`/`saveState` must finish an atomic durable encrypted commit before returning. Raw signed transactions must not enter public run JSON, logs or browser responses. All dependencies are rechecked for canonical receipts in bounded batches of eight before a new signed write and before a restarted worker publishes. A reorganization of an already recorded receipt requires reconciliation. Activation intents persist their fixed sale-start-plus-60-seconds broadcast deadline. Generic crash reconciliation enforces that deadline immediately before broadcasting, while an already submitted transaction may finish confirming after it.

The operator's chain journal and its entry in `SepoliaRehearsalState.journals[operator.address]` must be the **same journal** because chain operations and rehearsal funding use one sequential nonce stream. Every chain save callback must enforce the aggregate rehearsal spend as well as persist the common run state. `transactionSpend` provides the accounting helper. Funding transfers and subsequent mint values both count toward the conservative cap; this is a spending-control ceiling, not a net economic loss estimate.

## Persistent 50-wallet Sepolia rehearsal

`ensureSepoliaWallets({chainId,path,masterKey,create})` creates exactly 50 unique wallets on the first explicit creation and thereafter opens the same vault. The caller supplies a 32-byte hexadecimal master secret. The vault uses AES-256-GCM with chain/version authentication, a private file, atomic rename and an exclusive lock. A wrong key, corrupted/empty vault or public file permissions fail closed. Preserve this vault and its master secret between runs. Never publish or log the returned Wallet objects, private keys or environment-file contents.

`runSepoliaRehearsalStep(options, round)` performs at most one transaction per tick and first reconciles any pending signed transaction. It verifies the exact prepared V9/V10 version, algorithm and cap, reads each recipient's cumulative primary mint counter and respects the actual remaining supply. A 1,000-ticket collection therefore uses all 50 recipients at 20 tickets each. Smaller collections stop at their actual supply; more than 1,000 tickets is rejected for this fixed-size rehearsal.

The existing operator, explicitly supplied old test donors and the 50 managed wallets provide existing Sepolia ETH. Only each recipient's shortfall is transferred; donor wallets retain their own outstanding mint allocation and gas. No environment secrets are scanned to discover donor accounts, and no wallet outside this explicit set can be spent from. After reveal the managed winning holders claim their own prizes. On unsold expiry the worker scans at most 20 token IDs per tick and refunds only NFTs owned by a managed wallet. Burned-token reads are distinguished from RPC failures.

Optional `recycleOperatorFunds` is Sepolia-only: after managed prize claims it returns only the actual collection owner's released surplus, growth reserve and unused VRF subscription funding to that owner. Contract accounting continues to protect unclaimed prizes, affiliate earnings and refunds. It never drains protected reserves. All reclaimed ETH can support later collections, although VRF and transaction gas are consumed and new funding may eventually be needed.

## Mixed-version indexing

Keep historical V8/V9 claims indexed when adding V10. The indexer accepts `INDEXER_TRUSTED_FACTORIES_JSON`, an explicit list of up to eight `{contractVersion,factory,factoryCodeHash}` objects on its configured chain. Each factory gets an independent reader and exact trust pin; V10 never inherits V8/V9 trust. V10 uses `INDEXER_V10_TRUSTED_FACTORY` / `INDEXER_V10_TRUSTED_FACTORY_CODEHASH`. Its award combinations decode identity rather than score, and it is excluded from the historical metadata-refresh queue. Existing single-factory environment settings still work when the list is absent. Add new public factory pins and provider address filters operationally; source changes do not update hosted environment settings or QuickNode filters.

## Local verification

The engine delays public catalog registration and collection-name projection until the collection announcement root is confirmed. The season's first confirmed root immediately starts the color/date forecast, even if a later thread reply requires reconciliation. Production lifecycle work precedes optional older Sepolia claims; a persisted round-robin keeps those claims progressing afterwards. Public freshness records the last successful canonical read, not repeated writes of stale state. All season-summary metrics use one shared confirmed block/hash via `snapshot(round, blockNumber)`.

Run `node --import tsx --test scripts/season-runner/chain-transactions.test.ts scripts/season-runner/sepolia-wallets.test.ts`, contract tests covering historical V4/V9 and V10 round/registry lineages, and indexer tests. These cover persistence-before-broadcast, crashes, canonical receipt changes, nonce conflicts, fee/spend caps, vault reuse/encryption, Mainnet rejection, 20-ticket mint behavior, completed-V8 source-only migration and independent mixed-version pins. Tests use local contracts or mocked providers; they are not evidence of live deployment, VRF, Twitter delivery, wallet funding or hosted indexing.
