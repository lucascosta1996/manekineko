# Shared contract interface

Run `npm run contracts:export` from the repository root to regenerate the ABI and source JSON files in `src/`. Consumers may import `@manekineko/contract-abi/round`, `@manekineko/contract-abi/factory`, and `@manekineko/contract-abi/round-source`. The source snapshot powers the predeployment contract viewer and is generated directly from Solidity, not copied by hand. This package contains no keys, provider credentials, bytecode, or hard-coded deployment addresses.

V2 exports use `/round-v2`, `/factory-v2`, and `/round-v2-source`. Affiliate-enabled V3 exports use `/round-v3`, `/factory-v3`, `/renderer-v3`, and `/round-v3-source`. The V3 source snapshot includes its immutable on-chain SVG renderer and unchanged unique-ranking library. A source snapshot is not explorer verification of a deployment.

## V7 draft implementation: two awards and scheduled seasons

V7 is a new deployment version (`affiliate-v7`, `unique-rank-v4`). Existing deployed collections and V4/V5/V6 artifacts keep their original rules. It is not independently audited or deployed by this change.

- `prizeBps` is the combined prize budget; V7 requires two positive awards; award 1 receives `prizeBps-secondPrizeBps` and award 2 receives `secondPrizeBps`. The first award must be at least as large as the second.
- `AwardRank` rejection-samples the `N*(N-1)` ordered-pair space from the deterministic, domain-separated VRF stream. Each pair has equal probability under the VRF/Keccak assumption. It then rotates/swaps a unique score permutation so the selected NFTs own the two highest ranks. This is **not** a full independent shuffle of every rank. Four displayed numbers still use the reversible on-chain `ScrambledRank` encoding.
- Only the current winning NFT holder can call `claimPrizeForRank(rank, recipient)` immediately after reveal. `claimPrize(recipient)` aliases rank 1. There is no owner prize-distribution function. A wallet holding both winning NFTs can claim both, independently. Winning NFTs stay transfer-locked until their own claim; other tickets unlock at reveal.
- `readyForNextRound()` means sold out, revealed, and every unclaimed liability backed. Rollover does not wait for holder claims. `prizePaid` still means all configured awards have been claimed, while `prizePaidAmount` is cumulative and the legacy settlement holder/time fields describe the first prize only.
- A position qualifies by reaching `minAffiliateReferrals` paid tickets. Qualified positions earn exactly equal amounts: `min(pool / qualifiedCount, lowestQualifiedReferralRevenue * affiliatePayoutCapBps / 10000)`. No referrals, vacant positions, and sub-threshold positions earn nothing. The cap limits disproportionate rewards; it does not establish human identity or eliminate multi-wallet self-referrals.
- `unallocatedAffiliatePool()` is the full undistributed budget at sellout, including rounding. `growthReserveBalance()` subtracts explicit `withdrawGrowthReserve` withdrawals. Ordinary operator `withdraw` protects this reserve, both prizes and all affiliate claims. The owner can explicitly withdraw the growth reserve after reveal; this is transparent treasury accounting, **not an enforced restriction on how off-chain treasury money is spent**.
- `saleStartAt` is an immutable UTC timestamp. Enrollment closes at that time; activation and minting cannot happen earlier. Deployment tools derive the full mint window from `saleStartAt + mintDurationSeconds`. The future keeper must activate at/after opening. A delayed keeper can delay opening, but cannot open early or shift the announced timestamp silently.
- V7 has a dedicated immutable renderer and an immutable creation-code deployer. The initcode is held in two inert `STOP`-prefixed code stores to stay within EIP-170, then copied for `CREATE`. This is not a proxy or an upgrade mechanism. Preflight checks both code-store bytes against the reviewed round creation bytecode.

### Registry migration

`ManekinekoAffiliateEligibilityV2` admits both V6 and V7, imports historical completed V5/V6 rounds as sources, and recognizes revealed/funded V7 predecessors without awaiting every prize claim. The EIP-712 enrollment schema and domain version remain `4`; the gate version is `affiliate-eligibility-v2`.

`ManekinekoWinnerCreditsV3` exposes `creditsForAward`, `claimAwardCredit`, `redeemAward`, and `claimAndRedeemAward`, with rank-1 legacy aliases. The beneficiary is the settled NFT holder, never the chosen prize payment address. Each wallet may consume one lifetime sponsored mint across both awards. For V7, the earning time is the immutable reveal timestamp so preparing the next collection before a delayed claim does not erase eligibility.

The V3 registry constructor takes `(owner, historicalWinnerRoot, previousRegistry)`. A prior V2 registry must have zero outstanding sponsorship, and prior `redeemedSource` is checked on issue and redemption. **Migration must permanently retire funding and mint targets on that older registry.** The old immutable registry cannot enforce the new registry's lifetime state; re-funding a still-open old mint target could otherwise permit old-after-new double use. Canonical address/hash pins and operational retirement are required before adopting V3. There are no live registry changes in this implementation.

V7 deployment tools default to read-only preflight. `round-v7.sepolia.example.json` intentionally uses an unresolved zero start timestamp and invalid placeholder addresses; replace them with reviewed values before preflight. `V7_BROADCAST=1` and a dedicated journal are explicit prerequisites to broadcast. Social posts and a scheduler are outside these tools.

Unsigned registry setup supports `scripts/affiliate-eligibility-operations.mjs deploy --version v2` and `scripts/winner-credit-operations.mjs deploy --version v3` (with their required chain, owner and output arguments). Legacy V6 admission sources can be imported with `legacy --version v2 --source-version v6`. V7 admission uses `AFFILIATE_ELIGIBILITY_V2_ADDRESS_<chain>` / `AFFILIATE_ELIGIBILITY_V2_CODEHASH_<chain>`; credit V3 uses the canonical `WINNER_CREDITS_ADDRESS_<chain>` / `WINNER_CREDITS_CODEHASH_<chain>` and the reviewed migration pins `WINNER_CREDITS_PREVIOUS_ADDRESS_<chain>` / `WINNER_CREDITS_PREVIOUS_CODEHASH_<chain>`. Existing V6 command defaults remain unchanged. These helpers only write unsigned operation plans.

## V8 equal prizes for six winning NFTs

V8 (`affiliate-v8`, `unique-rank-v5`) adds immutable `winnerCount` instead of V7's `secondPrizeBps`. Its default launch plan has 1,000 tickets at 0.01 ETH, a total `prizeBps` of 6000, and `winnerCount=6`: exactly six distinct winning NFTs each receive 1 ETH at sellout. Counts from 1 to 10 are supported when supply is sufficient and the positive total prize basis points divide evenly by the count. V7 remains a separate two-prize version with its existing unequal prize terms.

`MultiAwardRank` rejection-samples one uniform integer in the ordered-winner sample space `N*(N-1)*...*(N-K+1)`. The sample space fits in 160 bits at the supported limits. Mixed-radix decoding chooses uniformly among remaining tokens at each step, without replacement; every ordered K-tuple corresponds to exactly one sample-space value. The round retains a deterministic VRF-bound rejection cursor, freezes all winners atomically on acceptance, and permits no entropy selection or rerolls. The selected NFTs receive the highest K unique scores. Remaining NFTs receive the other unique scores in token order: this does **not** claim to randomly shuffle every losing rank. The independently domain-separated, reversible number-display encoding is unchanged.

All award events/getters and holder-only claim functions keep the V7 shape, with ranks 1 through `winnerCount`. `prizeAmountForRank` is identical for every winning rank. One wallet can own and claim multiple winning NFTs; the lifetime sponsored-mint reward still remains one per wallet. Unclaimed awards, affiliate liabilities and the growth reserve remain separately protected, while preparing a subsequent collection does not wait for holder claims.

V8 uses `ManekinekoAffiliateEligibilityV3` (`affiliate-eligibility-v3`) and `ManekinekoWinnerCreditsV4` (`winner-credits-v4`). The new eligibility gate can import prior completed V5/V6/V7 rounds as sources; new V8 rollover uses revealed, fully backed prizes. Credit V4 accepts a prior V2 or V3 registry. When migrating from V3 it calls that registry's lifetime predicate, preserving any inherited V2 redemptions instead of checking only V3's local spent mapping. The permanent retirement of sponsorship on all older registries remains an operational migration prerequisite.

`v8-config` and versioned V8 preflight/deployment scripts preserve fixed `saleStartAt` and derive the entire mint duration from that timestamp. V8 uses `AFFILIATE_ELIGIBILITY_V3_ADDRESS_<chain>` and `AFFILIATE_ELIGIBILITY_V3_CODEHASH_<chain>`. The V8 examples deliberately retain unresolved or invalid placeholders; no V8 deployment or live migration is performed by these code changes.
