# U2 and Web-side U4 implementation — 2026-09-27

This report covers the wallet, prize and affiliate Web work in `bots-run-notes-2-astra-ultra-2026-09-27.md`. It describes local source and verification, not a deployed release or authorization to operate the rehearsal.

## Implemented behavior

- Ranked collection claims, the prize hub, minting and affiliate enrollment use explicit provider/account selection. EIP-6963 and concrete legacy injected providers remain supported; an explicitly selected second authorized account is preserved. NFT discovery retains its read-only account selector. Connecting alone never submits a claim or mint.
- Prize cards show the selected account, ticket and amount; only the active prize reports checking, wallet confirmation or receipt waiting. Other claims are disabled during one operation. Wrong-holder feedback includes the ticket and a switch-wallet action. Draw-pending, already-paid, wrong-network, rejected, disconnected, expired and unavailable-verification states remain distinguishable.
- Claim preflight verifies the live chain, runtime hash, protocol/algorithm and frozen economic terms, completed draw, winning token, unpaid amount and current owner, then simulates the holder's exact claim and rechecks account/network before submission. Claims pay the selected holder account. A transfer before submission fails the old holder's simulation/preflight; existing prize history still attributes payment to its original claimant and recipient.
- Durable transaction intent is saved before the wallet request using the existing sessionStorage journal. Recovery is bound to the original rank, wallet, contract, chain, calldata, value and nonce. Refresh never resubmits; an ambiguous response asks for the original hash and checks it. A pending claim on one winning NFT cannot be mistaken for another claim held by the same wallet.
- Confirmed receipts remove the local card's action immediately and emit `tincta:prize-confirmed`; public collection polling refreshes on that event. `lib/prizes/confirmed.ts` saves receipt/block identity across refresh. `readConfirmedPrizes(collectionId, observedBlock)` only returns confirmations newer than the collection observation, so newer canonical state takes precedence over an old local success, including after a reorganization. Root U1 integrates this with the collection CTA. Ranked results have the `#prizes` anchor.
- Referral URLs retain existing server verification and fresh on-chain `affiliateWallet(slot)`/self-referral validation. Invalid referrals block the mint and offer an explicit direct-mint navigation, never an automatic fallback. The UI shows the beneficiary's full address and qualification/sellout terms. Minting now also explicitly simulates the transaction; its confirmed receipt and affiliate attribution are visible.
- The affiliate view polls a new read-only `/api/collections/[collectionId]/affiliates/activity?wallet=...` endpoint every 15 seconds while active. It verifies the enrolled wallet/slot and count at a canonical snapshot, discovers the latest 20 indexed `AffiliateReferralRecorded` events, then independently verifies each canonical successful receipt and decoded attribution. First-party notices deduplicate chain/contract/block-hash/transaction/log identity in localStorage. Replaced observations remove orphaned notices; failures retain a visibly stale last observation. Counts, qualification, estimated/accrued/available/claimed amounts and explicit commission claims retain the existing equal-share/cap contract calculation.

## Mobile connection choice and configuration

The source now lazily initializes **Reown AppKit 1.8.24** only after an explicit WalletConnect/mobile choice. Its built-in UniversalAdapter supplies the EIP-1193 connection; the application's existing ethers BrowserProvider and simulation/journal flow remain the only transaction path. This follows Reown's [AppKit integration for Ethereum providers](https://docs.reown.com/advanced/providers/ethereum). The deprecated `showQrModal` integration is not used. The optional ethers adapter was evaluated and removed because its eagerly imported Coinbase/Base path required unrelated x402 optional modules in the current Next build; AppKit's built-in UniversalAdapter is supported by the documented adapter-free setup and local SDK source.

Set the public `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` at build time and configure the exact deployment/localhost origins in the Reown project's allowlist. Metadata uses the current origin. The setting is documented in `apps/web/.env.example`; no project ID, hosted environment or permissions were changed. Without it, the app explicitly says mobile WalletConnect is unavailable and retains injected/in-app-browser choices. Analytics, social/email login, swaps, onramp, send and unrelated injected/Base/Coinbase SDK options are disabled. A connected wallet's advertised HTTPS universal redirect can supply an **Open connected wallet** action; no wallet deep link is guessed and the app does not claim a popup has opened.

Official references checked on 2026-09-27: [Reown Next installation](https://docs.reown.com/appkit/next/core/installation), [Ethereum provider and AppKit](https://docs.reown.com/advanced/providers/ethereum), [Reown project/origin allowlisting](https://docs.reown.com/walletkit/ios/cloud/relay). Real WalletConnect relay approval, extension behavior and mobile redirects still need the configured project and device acceptance.

## Manual role import boundary for U4

The runner's role reservation and private one-role encrypted keystore export are owned by the companion U4 implementation. No wallet was accessed or exported during this work.

Current [MetaMask official import guidance](https://support.metamask.io/start/use-an-existing-wallet) supports **JSON keystore import on Extension only**: account selector → Add wallet → Import an account → Select Type → JSON File → choose the selected role's local file → enter that file's password → Import. The password is the keystore password, not the MetaMask application password. Enable/select Sepolia through the wallet's [test-network controls](https://support.metamask.io/configure/networks/how-to-view-testnets-in-metamask), then compare the imported public address to the sanitized run sheet before selecting it in Tincta. These are documentation-verified instructions; no actual import was performed.

Do not describe JSON import as working on MetaMask Mobile or assume imported accounts synchronize to another device. The encrypted-keystore rehearsal should initially target an explicitly tested compatible extension. Any additional mobile import mechanism/device remains a separate verified dependency; the application never needs private-key input.
