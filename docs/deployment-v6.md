# V6 varied on-chain combinations

V6 keeps the V5 pool economics, VRF draw, unique ranks, holder claim rules and immutable SVG artwork. It changes how a rank is encoded as four numbers, records `winningHolder` and `prizePaidAt` for the [winner credit program](winner-credits.md), and adds [NFT ownership eligibility for affiliate enrollment](affiliate-holder-eligibility.md). Existing V5 contracts and NFTs cannot be upgraded or cosmetically rewritten; a new collection requires a new V6 factory.

## Number generation

Scores still range from 1 through the collection supply, each exactly once. The VRF-derived rotation selects which ticket receives each rank and the unique maximum. This is not a uniformly shuffled assignment of all ranks.

After reveal, `combinationKey()` derives a separate public key from the original VRF word, chain ID, collection address, round ID and supply, using domain `MANEKINEKO_COMBINATION_V3`. Four Feistel rounds permute the 16-bit value `rank - 1`, then split the encoded value into four digits from 1 to 16. The permutation is bijective for every key, so no two tickets in a collection have the same combination. The immutable renderer supplies the pure encoding and inverse implementation; the round's `scoreCombination([a,b,c,d])` verifies and decodes the numbers to their original rank.

The key is revealed publicly and is not encryption. The encoding adds visual variation, not randomness or entropy to the draw. Repeated digits and prefixes remain possible by chance. There is no reroll or filtering to select a preferred visual result, and no extra VRF request, per-ticket state write, or collection scan.

For a fixed **test key** (not a live collection), rank 1 encodes as `12 / 15 / 3 / 1`, rank 2 as `6 / 5 / 11 / 3`, and rank 20 as `10 / 15 / 9 / 7`. The largest displayed digit or packed code does not determine the winner; the decoded score does.

## Prepare and deploy a new collection

1. Apply database migrations `016_scrambled_rank_v6.sql` and `017_affiliate_holder_eligibility.sql` after testing them on an isolated database. Deploy the updated web, launch and indexer applications together with the generated V6 ABIs.
2. Prepare both canonical registries using the [credit setup workflow](winner-credits.md) and [affiliate eligibility workflow](affiliate-holder-eligibility.md). Create a V6 launch configuration with both addresses and a separate sponsorship budget. It contains `contract.algorithmVersion: "unique-rank-v3"`. Previously saved documents retain their version and finalized documents stay immutable. The offline `launch:prepare` command emits `round-v6.json`, the V6 deployment plan and unsigned credit/eligibility setup plans.
3. Set `V6_CONFIG_PATH`, `V6_PREFLIGHT_FROM`, `V6_AFFILIATE_ELIGIBILITY_ADDRESS`, the canonical eligibility address/hash pair and the appropriate RPC, then run `npm run v6:preflight:sepolia --workspace @manekineko/contracts`. This is read-only. Do not reuse a V5 factory address or journal.
4. Broadcasting requires `V6_BROADCAST=1`, an explicit private `V6_JOURNAL_PATH`, a funded staging signer, and the deployment network. `v6:deploy:sepolia` stops before activation; an unregistered target reports `funded-awaiting-affiliate-registration`. Register it in the eligibility registry before enrollment. Keep the durable journal for retries. The deployer checks chain, configuration fingerprint (including the gate), canonical receipts, nonce, runtime bytecode, balances and fee ceiling before sending each transaction. `V6_MAX_FEE_PER_GAS_WEI` defaults to 5 gwei.
5. Verify all four V6 components with Solidity 0.8.37, **viaIR=true**, optimizer **runs=1**, and Cancun EVM target. `scripts/verification-args-v6.cjs` reads constructor arguments from the V6 journal. V5 retains its historical compiler settings. Run `contracts:export` to enforce Ethereum runtime/creation size limits after any source change.
6. Configure `AFFILIATE_TRUSTED_FACTORY_V6_<chainId>` and `AFFILIATE_TRUSTED_FACTORY_CODEHASH_V6_<chainId>` in the web application only after verifying that factory. Keep V5 pins for historical holdings. Register the new collection with `scripts/sync-staging-collection.mjs`, first in preview mode. The eligibility registry and canonical collection registration must verify before this tool enables admission.
7. Run a separate V6 indexer instance with `INDEXER_CONTRACT_VERSION=affiliate-v6`, `INDEXER_V6_TRUSTED_FACTORY` and `INDEXER_V6_TRUSTED_FACTORY_CODEHASH`. The existing V5 instance keeps its own factory. Collection queries, cursors and trust checks are version and factory scoped. Configure the V6 instance's cron/webhook as described in [automatic indexing](automatic-indexing.md).
8. Before activation, approve the reviewed factory in the canonical credit registry, register the collection and fund its sponsorship budget. Register after the previous winner's successful prize-payment timestamp. Rehearse enrollment, sponsored and direct minting, sellout, real VRF fulfillment, metadata display, winning-holder claim, the earned credit, affiliate claims and operator withdrawal on Sepolia before Mainnet qualification. Explorer image indexing remains controlled by the external platform; [gallery refresh instructions](nft-gallery.md) still apply.

## Verification and release status

The source is a new version intended for qualification, not an upgrade to the completed 20-ticket V5 rehearsal. Local tests exercise the full 65,536-value encoding domain, 20/1,000/2,000-ticket uniqueness, JavaScript/Solidity parity, metadata, unchanged economic reserves and holder-only recovery. Local chain/database integration exercises direct mint indexing, the V6 winner archive and rollback after reorganizations. These checks do not replace a live V6 Sepolia rehearsal or an independent audit.
